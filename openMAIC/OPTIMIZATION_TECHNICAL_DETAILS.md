## Problem Analysis

### Problem #1: N+1 Query Performance Crisis

**The Inefficient Code (Before):**
```typescript
// app/api/student/quizzes/route.ts (lines 92-123)
const quizzesWithScores = await Promise.all(
  quizzes.map(async (quiz: any) => {
    // ❌ QUERY 1 per quiz: Get best score
    const { data: bestAttempt } = await supabase
      .from('quiz_submissions')
      .select('percentage')
      .eq('student_id', studentId)
      .eq('quiz_id', quiz.id)           // Different for each quiz!
      .eq('status', 'graded')
      .order('percentage', { ascending: false })
      .limit(1);

    // ❌ QUERY 2 per quiz: Get access type
    const { data: access } = await supabase
      .from('quiz_access')
      .select('access_type')
      .eq('student_id', studentId)
      .eq('quiz_id', quiz.id)           // Different for each quiz!
      .single();

    return { ...quiz, student_best_score, access_type };
  })
);

// TOTAL QUERIES:
// - 1 quiz list query
// - 20 best_score queries (1 per quiz)
// - 20 access_type queries (1 per quiz)
// = 41 QUERIES! ❌
```

**Why This Happens:**
The `Promise.all()` creates 20 parallel async operations, each making 2 database calls. This is called the **N+1 query problem**:
- 1 query to fetch N results
- N additional queries (one per result)
- Total: 1 + N + N = 2N + 1 queries instead of 1

**Performance Impact:**
- Each database round-trip: ~50–100ms
- 41 queries × 50ms = ~2,050ms = **2+ seconds**
- Dashboard appears slow, unresponsive

### Problem #2: Streak Race Condition

**The Unsafe Code (Before):**
```typescript
// lib/student/gamification/streaks.ts (old version)
export async function updateStreak(...) {
  // ❌ STEP 1: Read current streak (UNPROTECTED)
  const { data: currentStreakData } = await supabase
    .from('student_streaks')
    .select('*')
    .eq('student_id', studentId)
    .eq('quiz_id', quizId)
    .single();                    // <-- No locking!

  let currentStreak = currentStreakData.current_streak || 0;  // Read: 5

  // ❌ STEP 2: Do calculations (during this time, another request might also read!)
  if (isYesterday(...)) {
    currentStreak += 1;           // Calculate: 5 + 1 = 6
  }

  // ❌ STEP 3: Write result (but it's not atomic!)
  await supabase
    .from('student_streaks')
    .upsert({
      current_streak: currentStreak,  // Write: 6 ❌
      ...
    });
}
```

**Race Condition Scenario:**
```
Timeline:
┌─ Request A (Quiz 1 submitted)
│   └─ T1: Read streak = 5
│   └─ T2: Calculate streak = 6
│   └─ T4: Write streak = 6 ❌
│
└─ Request B (Quiz 2 submitted, concurrent)
    └─ T1: Read streak = 5         ← Same value!
    └─ T3: Calculate streak = 6
    └─ T5: Write streak = 6 ❌     ← Should be 7!

Result: Both requests see 5, both calculate 6
Database ends up with 6 instead of 7 ❌
```

**Why This Matters:**
- Streak is a critical user achievement metric
- Users notice when streak doesn't increment correctly
- Concurrent submissions are common on slow networks (retries)
- This bug is hard to reproduce and diagnose

## Solutions Implemented

### Solution #1: Use Database-Level JOINs and Aggregation

**The Optimized Code (After):**
```typescript
// app/api/student/quizzes/route.ts (lines 92-123)
const { data: enrichedQuizzes } = await supabase
  .from('quizzes')
  .select(`
    id,
    title,
    description,
    difficulty,
    duration_minutes,
    pass_rate,
    industry,
    quiz_access!left(access_type),              // ← LEFT JOIN
    quiz_submissions!left(percentage)           // ← LEFT JOIN
  `)
  .eq('quiz_access.student_id', studentId)     // Filter access
  .eq('quiz_submissions.student_id', studentId)
  .eq('quiz_submissions.status', 'graded')
  .in('id', quizzes.map(q => q.id));

// Transform: Extract best score from submissions array
const quizzesWithScores = enrichedQuizzes.map(quiz => {
  const bestScore = quiz.quiz_submissions?.length > 0
    ? Math.max(...quiz.quiz_submissions.map(s => s.percentage))
    : null;

  return {
    ...quiz,
    student_best_score: bestScore,
    access_type: quiz.quiz_access?.[0]?.access_type || 'none',
  };
});

// TOTAL QUERIES:
// - 1 query with JOINs ✅
// Performance: 41 queries → 1 query
```

**How This Works:**
```sql
-- Equivalent SQL generated by Supabase:
SELECT
  q.*,
  qa.access_type,
  qs.percentage
FROM quizzes q
LEFT JOIN quiz_access qa
  ON q.id = qa.quiz_id AND qa.student_id = $1
LEFT JOIN quiz_submissions qs
  ON q.id = qs.quiz_id
  AND qs.student_id = $1
  AND qs.status = 'graded'
WHERE q.id IN ($2, $3, ... $21)
```

**Why This Is Better:**
- ✅ Single database round-trip (instead of 41)
- ✅ Database optimizer handles efficient JOIN strategies
- ✅ Indexes on `quiz_access.student_id` and `quiz_submissions.student_id` are used
- ✅ Results come back as nested arrays: `quiz.quiz_submissions = [...]`

**Trade-Off:**
- Code transforms nested array data instead of receiving flat result
- Requires understanding Supabase PostgREST conventions for LEFT JOINs
- Memory: Response includes all submissions/access rows (mitigated by filtering in WHERE clause)

### Solution #2: Use Database-Level Locking (SELECT FOR UPDATE)

**The Atomic Function (After):**
```sql
-- supabase/migrations/023_fix_performance_and_races.sql
CREATE OR REPLACE FUNCTION update_streak_atomic(
  p_student_id UUID,
  p_quiz_id UUID,
  p_user_timezone VARCHAR,
  p_now TIMESTAMPTZ
)
RETURNS TABLE(
  current_streak INTEGER,
  longest_streak INTEGER,
  streak_continued BOOLEAN,
  badge_7day_awarded BOOLEAN,
  last_quiz_date DATE
) AS $$
DECLARE
  v_current_streak INTEGER;
  v_longest_streak INTEGER;
  v_last_quiz_date DATE;
BEGIN
  -- ✅ CRITICAL: Lock the row to prevent other transactions
  -- from reading/writing it concurrently
  SELECT current_streak, longest_streak, last_quiz_date
  INTO v_current_streak, v_longest_streak, v_last_quiz_date
  FROM public.student_streaks
  WHERE student_id = p_student_id
    AND quiz_id = p_quiz_id
  FOR UPDATE;  -- ← MAGIC: Database-level exclusive lock

  -- Now safe to read, calculate, and write
  -- Because lock prevents ANY other transaction from accessing this row
  v_current_streak := COALESCE(v_current_streak, 0);
  
  IF v_days_since_last = 1 THEN
    v_current_streak := v_current_streak + 1;  -- Safe calculation
  ELSE
    v_current_streak := 1;
  END IF;

  -- ✅ Write is guaranteed to be atomic
  -- Because lock was held during read → calculate → write
  INSERT INTO public.student_streaks (...)
  VALUES (p_student_id, p_quiz_id, v_current_streak, ...)
  ON CONFLICT (student_id, quiz_id) DO UPDATE SET
    current_streak = v_current_streak;

  -- Implicit transaction commit releases the lock
  RETURN QUERY SELECT v_current_streak, v_longest_streak, ...;
END;
$$ LANGUAGE plpgsql;
```

**From TypeScript, Call It Like This:**
```typescript
// lib/student/gamification/streaks.ts (new version)
const { data, error } = await supabase.rpc('update_streak_atomic', {
  p_student_id: studentId,
  p_quiz_id: quizId,
  p_user_timezone: userTimezone,
  p_now: now.toISOString(),
});

const result = data[0];  // { current_streak: 6, streak_continued: true, ... }
```

**What Happens with Two Concurrent Requests:**
```
Timeline (WITH FOR UPDATE locking):
┌─ Request A (Quiz 1 submitted)
│   └─ T1: SELECT...FOR UPDATE streak  ← LOCK acquired, row is locked
│   └─ T1: Read streak = 5
│   └─ T2: Calculate streak = 6
│   └─ T4: UPSERT streak = 6
│   └─ T4: Transaction commits, LOCK released
│
└─ Request B (Quiz 2 submitted, concurrent)
    └─ T1: SELECT...FOR UPDATE streak  ← WAITS for lock (Request A has it)
    └─ T4+: LOCK acquired (now row is unlocked from A)
    └─ T5: Read streak = 6             ← Different value! (A already wrote)
    └─ T6: Calculate streak = 7
    └─ T8: UPSERT streak = 7
    └─ T8: Transaction commits, LOCK released

Result: Request A → 6, Request B → 7 ✅ Correct!
```

**Why SELECT FOR UPDATE Works:**
1. **Mutual Exclusion:** Only one transaction can hold the lock at a time
2. **Serial Execution:** Concurrent requests are serialized (one after another)
3. **Atomicity:** Read → Calculate → Write is atomic as a single unit
4. **Deadlock Prevention:** PostgreSQL detects and prevents circular locks

**Trade-Offs:**
- ✅ Prevents race conditions completely
- ✅ Works across multiple server instances (database-level guarantee)
- ❌ Slightly slower than non-locking code (lock acquisition overhead ~1-5ms)
- ❌ Could block if many concurrent updates (but typically <5 concurrent streaks)
- ✅ Lock is released immediately after function completes (not held long)

## Database Indexes Added

**Why Indexes Matter:**
```sql
-- OLD (NO INDEX):
-- Request A: SELECT...FOR UPDATE from student_streaks
--   → PostgreSQL does FULL TABLE SCAN
--   → Locks ALL rows while scanning
--   → Returns matching row
-- This is bad: Every update locks the entire table!

-- NEW (WITH INDEX):
-- Request A: SELECT...FOR UPDATE from student_streaks
--   → PostgreSQL uses index: idx_streaks_student_quiz_for_update
--   → Jumps directly to matching row
--   → Locks only that row
-- Much better: Only one row is locked!
```

**Indexes Created:**
```sql
-- Index for efficient streak lookups and locking
CREATE INDEX idx_streaks_student_quiz_for_update
  ON student_streaks(student_id, quiz_id)
  WHERE current_streak >= 0;

-- Index for quiz access lookups (used in dashboard)
CREATE INDEX idx_quiz_access_student_quiz
  ON quiz_access(student_id, quiz_id);

-- Index for quiz submissions filtering (used for best score aggregation)
CREATE INDEX idx_quiz_submissions_student_quiz_graded
  ON quiz_submissions(student_id, quiz_id, status)
  WHERE status = 'graded';
```

**What These Do:**
- `(student_id, quiz_id)` composite index: Quick lookup for specific streak
- `status = 'graded'` partial index: Only indexes graded submissions (saves space)
- Enables query planner to use indexes for JOIN conditions

**Performance Improvement:**
```
Before indexes:
  - SELECT...FOR UPDATE: ~50-100ms (full table scan)
  - Lock held for 100ms

After indexes:
  - SELECT...FOR UPDATE: ~1-2ms (index lookup)
  - Lock held for 1-2ms (much shorter!)
```

## Query Optimization: Dashboard Example

**Before (Multiple Separate Queries):**
```typescript
// Query 1: Get quiz access list
const quizzes = await supabase
  .from('quiz_access')
  .select(`quiz_id, access_type, quizzes(...)`)
  .eq('student_id', studentId);                    // 1 query

// Query 2: For each quiz, get best score
const bestScores = await Promise.all(
  quizzes.map(qa =>
    supabase.from('quiz_submissions')
      .select('percentage')
      .eq('student_id', studentId)
      .eq('quiz_id', qa.quiz_id)                  // N queries
  )
);

// Query 3: Count total quizzes
const { count: totalQuizzes } = await supabase
  .from('quiz_access')
  .select('id', { count: 'exact' })
  .eq('student_id', studentId);                   // 1 query

// Query 4: Count completed quizzes
const { count: completed } = await supabase
  .from('quiz_submissions')
  .select('id', { count: 'exact' })
  .eq('status', 'graded');                        // 1 query

// Query 5: Get badges
const badges = await getStudentBadges(studentId);  // 1+ queries

// Query 6: Get current streak
const streak = await supabase
  .from('student_streaks')
  .select('current_streak_days')
  .limit(1);                                       // 1 query

// TOTAL: 1 + N + 1 + 1 + 1+ + 1 = 5 + N queries
// For 20 quizzes: 5 + 20 = 25+ queries total ❌
```

**After (Single Optimized Query):**
```typescript
// Single query with all JOINs
const { data: quizzesWithAccess } = await supabase
  .from('quiz_access')
  .select(`
    quiz_id,
    access_type,
    quizzes(*),
    quiz_submissions!left(percentage)
  `)
  .eq('student_id', studentId)
  .eq('quiz_submissions.status', 'graded');  // 1 query ✅

// Calculate progress from data we already have
const myQuizzes = quizzesWithAccess.map(qa => ({
  ...qa.quizzes,
  student_best_score: Math.max(...qa.quiz_submissions.map(s => s.percentage)),
  access_type: qa.access_type,
}));

const completed = myQuizzes.filter(q => q.student_best_score !== null).length;
const completionPercentage = (completed / myQuizzes.length) * 100;

// Other queries (badges, streak, points) can remain separate
// TOTAL: 1 + 1 + 1 = 3 queries (was 25+) ✅
```
